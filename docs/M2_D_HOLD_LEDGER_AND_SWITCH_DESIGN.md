## M2-D implementation contract

M2-D implements a **private host-side dual-mode transaction** using the validated immutable CPU model and existing M2-B/C offscreen passes. It does not change `include/ars/ars.h`, public ABI capability bits, archive/schema bytes, source authority or motion semantics. The host owns one immediate context on R, an offscreen target and a monotonically changing generation; it supplies a committed pose/visibility snapshot and camera selection for a frame. The renderer must never read a mutable pose mid-draw. If the host does not yet have a committed-pose producer, add a private testable frame input with explicit generation and snapshot ownership rather than claiming production pose integration.

1. **Admission and prepare.** Validate requested representation and matching asset support before GPU calls. Capture the old mode, pose generation, target pixel/frame hash and live-object identities. Build the candidate CPU draw snapshot with checked host allocator/budgets, then preflight and create all candidate GPU resources before publishing a new mode. A missing mode, unsupported material, invalid camera/target or CPU/GPU allocation failure returns a typed error and leaves the old representation, pose, target and resource set intact. Inject failure at each CPU/GPU allocation boundary and before query reservation; a test that only exceeds a preflight budget is insufficient for OOM rollback.
2. **Atomic commit and draw.** Only R may submit. One serialized host admission point covers both 2D and 3D and rejects old-generation targets before state mutation. Commit the new mode and its immutable pose/camera snapshot together after candidate readiness; a failed draw must have a defined rollback or quarantine path and must never silently expose a half-published mode. Preserve the existing 2D byte-space premultiplied alpha contract, 3D target/depth rules and all touched D3D host state. Host resize creates a new target generation and proves stale-target refusal.
3. **Retirement and close.** Keep independent pins for the CPU snapshot, candidate/old GPU bundle, target and exact event query until that query proves completion. A `BUSY` or failed `GetData` is not completion. Quarantine a lost generation. Replace the caller-supplied `host_quiesced` Boolean with a private receipt that only the host can issue after it blocks new admissions, drains/invalidates context users on R and surrenders old device/RTV references. Reject wrong-thread, forged, stale, early and duplicate receipts before releasing pins. The receipt proves protocol behavior under injection; only a later actual-loss run can close D06/D08.
4. **Direct verification.** First write RED controls for unsupported mode, every injected allocation site and invalid teardown receipt. Then run CPU transaction tests on Windows/Linux; WARP golden 2D/3D switch/readback, dynamic hide/show/opacity/Z, camera/pose commit, 100 switches and 100 resize/close cycles on Windows; repeat the bounded host cases on the named GTX 1060 with debug layer. Compare pre/post resource identities after releasing host-held references; record exact SHA, commands, exit codes, adapter/driver and raw log hashes. Run the existing M1/M2 regressions affected by the host seam. Record D02/D03 and G03/G04/G05 conclusions separately; do not roll them into a single “M2 PASS.”

## Checkpoints and stop conditions

| Checkpoint | Exit evidence | Stop / remain HOLD if |
| --- | --- | --- |
| D0: host seam and ownership | Reviewed ownership graph, committed snapshot input, R-thread admission and target generation; RED receipt controls; no public ABI delta. | Host cannot account for all immediate-context callers or snapshot ownership. |
| D1: candidate transaction | Missing-mode, wrong-generation, CPU/GPU injected OOM and pre/post-submit errors leave a known old or quarantined state; exact query pins demonstrated. | Any failure mutates old pose/frame or releases a pending resource. |
| D2: integrated pixels and switch | 100 switches plus resize and dynamic 2D/3D oracles on WARP and named GPU, debug identities, full affected CI on exact head. | G03/G04 prerequisites remain unproven, resource growth occurs, or only private harness output is available. |
| D3: physical loss (later runner) | Separate D06/D08 direct packet per [loss-verification design](M2_D06_D08_LOSS_VERIFICATION_DESIGN.md). | Disposable reset-capable runner or actual loss/recovery observation is missing; retain `HOLD_CARRY_TO_M2`. |

The next source PR should be stacked on the exact M2-C implementation head, keep the first three checkpoints independently reviewable, and update the M1-D machine-readable ledger only when a D-case has new direct evidence. If integrated host work reveals a material change to ownership, switching semantics or color/ABI contract, amend the relevant ADR and re-run impacted gate tests before considering promotion. Do not merge this design as proof of any gate, and do not advertise rendering or device-loss recovery until the separate public and physical acceptance paths are complete.
