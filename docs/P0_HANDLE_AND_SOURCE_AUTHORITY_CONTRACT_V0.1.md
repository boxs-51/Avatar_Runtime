## 1. Normative safety invariants

H1: A public handle is a by-value ID; NEVER a dereferenceable caller-supplied pointer.
H2: Every operation pins validated object storage in a registry before accessing it, and unpins afterward. Logical destroy is immediate; physical reclamation is deferred.
H3: Each slot generation increases monotonically and never wraps; exhausted slots are retired permanently. Runtime UID is process-unique and never reused.
H4: Close prevents new pins and new pose commits based on stale character/source generations. In-flight calls already pinned before close may safely finish a copy but may not resurrect the object.
S1: A source label, packet-provided source ID/generation/character/priority, and timestamp are NOT authority. The trusted host grants a capability, bound to ONE character and a fixed semantic-channel scope.
S2: A frame can influence a pose only if its source capability/generation is valid at both admission and final pose publication.
S3: Once revoke returns, no POSE COMMIT occurring afterward may depend on the revoked generation. Previously committed and already submitted GPU frames may remain visible until separate render synchronization.
S4: Queue and resource quotas are bounded; stale queued entries can be lazily discarded but must never publish.
T1: A trusted host serializes structural control with update, except specifically documented source revoke. Ingress may run concurrently. Render consumes immutable, pinned snapshots.
T2: In-process native code is in the trusted computing base. Bearer token protections do NOT sandbox arbitrary malicious native plugins.

## 2. By-value handle ABI

The design-only C header defines a 16-byte ars_handle_id_v1 token: uint64_t runtime_uid, uint32_t slot, uint32_t generation. Strong typedef wrappers are ars_runtime_h, ars_model_h, ars_character_h and ars_source_admin_h. Slot 0 is reserved for runtime. Zero/invalid tokens cannot refer to live objects.

A process-level metadata router maps active nonreused runtime_uid values to pinned runtime control blocks. This is only a routing metadata registry; it stores no global character, renderer, GPU device or asset cache. The UID is generated by a monotonic process-wide 64-bit counter and never reused; upon theoretical exhaustion, creation returns HANDLE_EXHAUSTED. Handles are process-local, non-secret identities, never accepted over IPC as authentication.

Each runtime maintains slot metadata:
- type_tag (runtime/model/character/source-admin), generation, lifecycle OPEN/CLOSING/DEAD;
- object control block, pin_count, ref_count and pending retirement status;
- character->model internal references, source->character scoped binding, render snapshot pins.

A lookup MUST:
1. Validate token layout and expected wrapper/type. Never cast token to an address.
2. Under router read lock, locate runtime_uid and increment a safe runtime pin if OPEN.
3. Under runtime handle-table lock, check slot exists, type matches, generation is current, owner runtime matches and slot is ACTIVE; acquire object operation pin BEFORE exposing payload pointer.
4. Release both registry locks. Access object through the pin without callbacks under locks.
5. Release object pin and runtime pin; retire resources only when all snapshots, CPU pins and GPU fences are cleared.

A stale/released ID fails before touching freed payload memory. Invalidation increments slot generation; when UINT32_MAX is reached, that slot is never reused. Reuse of slots with new generations is permitted, but reuse of a (runtime_uid,slot,generation) triple is forbidden.

Model asset ownership: ars_model_release_p0 invalidates its USER handle, not the internal model references held by live characters. ars_character_destroy_p0 invalidates the character USER handle, atomically revokes its bound source records, and schedules GPU resource destruction after pins/fences. Repeated destroy returns STALE_HANDLE, not a second free.

### 2.1 Close/teardown state machine

~~~mermaid
stateDiagram-v2
    [*] --> RUNNING
    RUNNING --> QUIESCING: begin_close / block new operation pins
    QUIESCING --> DRAINING: invalidate sources and chars
    DRAINING --> GPU_RETIRING: CPU work/snapshots quiescent
    GPU_RETIRING --> DEAD: device owner completes GPU retire
    DEAD --> [*]
~~~

begin_close, on the trusted control thread:
- first marks runtime QUIESCING under registry lock (linearization point);
- blocks future pins and source registration; revokes source generations and marks characters CLOSING;
- drops queued pending work, defers destruction of pinned payloads and schedules GPU retire on R thread;
- returns promptly, without waiting while holding locks or invoking host callbacks.

drain_gpu MUST run on owning render/GPU thread and respect D3D11 execution completion rules to be finalized in ADR-0001. query_close returns outstanding pins and GPU retirees; finish_close returns BUSY while work remains. On successful finish_close, remove runtime from router, release metadata and make every old handle STALE_HANDLE. If the host never pumps R, close may remain BUSY rather than freeing GPU memory on H unsafely.

Character destroy concurrent with ingress is supported by pins plus generation recheck. Structural destroy overlapping simulation update is NOT supported: return BUSY on detected conflict, and require host to invoke it at a quiescent point. Render may have a pinned previous immutable snapshot while character logically closes; retirement waits for the snapshot and GPU completion.

### 2.2 Locking and callback rule

Lock ordering is router lock -> runtime handle-table lock, then RELEASE before taking source/pose locks. Source revoke and pose publish acquire a short per-character publish_gate; no GPU lock or host callback under that gate. All GPU retire queue operations are independent after releasing the publish gate. Never synchronously wait S->R or R->S inside a callback. Host clock callback is thread-safe, non-reentrant, returns monotonic ns and is called outside internal locks.

## 3. Source authorization is capability-based

The trusted host owns source registration and controls which adapter is allowed to obtain an ingress capability. Untrusted network packets are authenticated at the adapter boundary and MUST NOT directly call the privileged registration API.

Two distinct types:
- ars_source_admin_h: ordinary generation-checked control handle used by the trusted host to rotate/revoke or release a source; must not be shared with untrusted adapters.
- ars_ingress_cap_v1: 128-bit bearer capability minted using an OS CSPRNG, unique among live capabilities; secret in trusted adapter memory; never logged, serialized, sent on network or placed in an asset file. RNG failure MUST abort source registration/rotation; no deterministic fallback.

A registration binds immutable grants:
- one exact runtime_uid + character handle generation;
- canonical semantic-channel ID allowlist; empty allowlist means DENY, no wildcard in v0.1;
- fixed motion priority, maximum channels/frame, ingress rate quota and TTL/lease;
- source generation minted by runtime, strictly increasing within the source record; a diagnostic label that is NOT authority.

Registration must copy and validate descriptor buffers before returning. Channel grants apply to the LOGICAL rig and remain the same when a character switches 2D/3D. Expanding scope requires registering a new source capability with trusted host approval; untrusted frame data cannot widen it. Camera/API/AI inputs all pass the same authorization gate.

### 3.1 Ingress admission algorithm

~~~text
submit(runtime_h, cap, frame):
  pin OPEN runtime via validated registry handle
  obtain trusted clock now_ns (outside locks)
  lookup cap in runtime capability map; pin live source and character
  verify ACTIVE, generation, character binding, TTL and quotas
  check frame ABI struct_size/version/flags, pointers, count/size overflow
  validate UTF-8 channel IDs, duplicate IDs, allowed semantic scopes
  validate typed finite values, bool/triggers, vector/quaternion units
  verify per-capability strictly increasing sequence and timestamp policy
  deep-copy data into a bounded queue
  stamp source generation AND character generation from runtime metadata
  return OK for queued frame, not a promise of pose publication
~~~

The public motion frame intentionally has NO source_id, caller-selected generation, character identity, requested priority or layer authority. source diagnostic labels from network packets cannot authorize a frame. The trusted clock callback and runtime update timestamps MUST use the same clock domain, and callback regressions return CLOCK_REGRESSION. Trusted ingress time, not caller-provided capture timestamp, determines token rate limits and TTL. A source capture timestamp is converted to the host time domain by a trusted adapter or marked ON_ARRIVAL.

Wrong/unknown/revoked capabilities return SCOPE_DENIED on ingress (do not disclose whether guessed secrets existed); quota, malformed type/value, wrong character generation or scope violations also fail without affecting pose. Validation and queue append must have clear linearization against rotation/revoke. Even if a pre-revoke submit appends after revoke, the later consumer and publication gate drop it.

## 4. Generation revoke and atomic pose publication

Source transitions:
- NEW -> ACTIVE on trusted registration (mint fresh random ingress cap, start generation).
- ACTIVE -> ACTIVE via ROTATE: atomically retire old ingress cap, increment generation, reset sequence window and mint a new independent token without widening scope.
- ACTIVE -> REVOKED via REVOKE, lease expiry, character close or runtime close.
- REVOKED -> CLOSED on admin release. Reuse of a source label never restores its earlier capability.
- CLOSED is terminal; re-registration creates a distinct source record and capability.

Runtime source generation is uint64_t and MUST never wrap. A frame-supplied generation, if seen in JSON at an adapter, is not authoritative. After rotate, an old cap is rejected regardless of old packet sequence, timestamp or source diagnostic label.

**Crucial pose linearization protocol:**

1. S collects and mixes candidate pose outside publish_gate, tagging every contributing source with its captured source generation.
2. Revoke obtains per-character publish_gate, sets status REVOKED and advances source epoch, then releases gate and returns.
3. Immediately before publish S obtains the SAME gate and rechecks all contributing sources/generations/leases. If any changed, abort candidate and recompute using only currently active inputs. The old candidate must NEVER be assigned a fresh pose_generation.
4. S publishes an immutable PoseSnapshot with release semantics; R acquires a reference/pin and reads only this snapshot.
5. Thus if publish linearizes first, it is historical before revoke; if revoke linearizes first, the old candidate is rejected. No future committed pose includes revoked input.

Old entries need not be synchronously removed from every queue: bound occupancy remains finite and the S consumer discards stale stamped generations.

**Important limitation:** revoke returning OK means no FUTURE pose commits from old capability. It does NOT erase already rendered pixels or automatically cancel already submitted GPU commands. Privacy-sensitive host behavior requires withholding old-frame presentation, performing a fresh fallback pose update/render and waiting for completion on R thread. Any stronger visual-scrub guarantee needs a separate explicit fence/API and review.

Revoke is a security exception allowed to race S. Rotate reuses the same gate to replace a capability/generation; may be called only by trusted H with structural updates otherwise quiescent. Character destroy and runtime close implicitly revoke all bound capabilities with the same barrier semantics.

### 4.1 Determinism, ordering, overflow

Sequence numbers increase strictly per capability generation; reaching UINT64_MAX requires rotation, never wrap. Timestamp reordering within an adapter-provided bounded jitter window is permitted only when sequence increases (timestamps and sequences are distinct concepts). No pose generation moves backward. Expired source ownership releases into an idle/other-authorized-layer baseline; old channel values must not be republished as a new pose generation after revoke. Continuous pose overflow can use bounded latest-wins, but discrete triggers need a separate bounded reliable queue or explicit failure status (no silent loss).

## 5. ABI declaration and status

See contracts/ars_p0_contract_draft.h for type-safe C99 declarations, compatible with C++20. Every extensible ABI struct starts with struct_size and abi_version. Output handles/caps MUST be initialized to zero on failure. All byte-array lengths and arithmetic validated before dereference/copy. Host callback pointers, clock_user_data and frame buffers have documented lifetime: frame is copied within submit, no caller pointers survive.

Methods covered:
- create/begin_close/drain_gpu/query_close/finish_close runtime;
- character_destroy, model_release;
- trusted source_register, source_revoke, source_rotate, source_admin_release;
- concurrent motion_submit and single-writer runtime_update.

The _p0 method suffix and contract filename explicitly indicate design-only interfaces. Production header still needs complete asset and rendering descriptors and a frozen ABI negotiation rule. A compilable declaration file is NOT evidence of a secure implementation.

## 6. Threat model boundary and open architecture decisions

Threats mitigated by design if correctly implemented: stale-handle UAF/ABA, concurrent logical destroy, frame replay after reconnect, packet-level spoofing through trusted adapters, cross-character or cross-channel injection, queue flood and expired sources retaining ownership.

Threats NOT mitigated here: malicious native library executing in same address space, compromised trusted host registering an overbroad scope, driver/device bugs, already presented GPU frames, cryptographic compromise of adapter memory. Untrusted native plugins require a separate process with OS-enforced sandboxing and authenticated IPC; not achieved by random tokens alone.
